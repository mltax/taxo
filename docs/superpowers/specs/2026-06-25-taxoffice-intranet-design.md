# 세무사무소 사내 웹페이지 — 설계 문서 (Design Spec)

- **작성일:** 2026-06-25
- **프로젝트 코드명:** taxo (사내 인트라넷)
- **상태:** 1차(MVP) 설계 확정

## 1. 목적 (Purpose)

세무사무소 직원들의 **커뮤니케이션과 복지**를 위한 사내 웹페이지. 자료 공유, 복지 청구·승인, 연차 청구·승인(결재), 건의사항 등 사내 업무를 웹으로 처리한다. 향후 모바일 앱으로 확장한다.

## 2. 범위 (Scope)

### 1차 (MVP) — 본 문서의 구현 대상
- 로그인 / 계정 관리 (관리자가 계정 발급)
- 복지 청구 · 승인 (결재 흐름)
- 자료실 (게시판 + 파일) · 공지사항

### 2차 (이후)
- 연차 청구 · 승인 (결재)
- 건의사항 · 댓글

### 3차 (이후)
- 네이티브 앱 / 푸시 알림

> 본 spec은 **1차(MVP)** 만 상세히 다룬다. 2·3차는 별도 spec으로 작성한다.

## 3. 사용자 / 권한 (Roles)

| 역할 | 권한 |
|------|------|
| **직원 (staff)** | 복지 청구 신청, 내 신청 현황 확인, 자료실 열람·다운로드, 공지 확인 |
| **결재자 (approver, 팀장/대표)** | 직원 권한 전부 + 승인 대기함 처리(승인/반려), 자료실 글·파일 등록 |
| **관리자 (admin)** | 직원 계정 발급·관리, 복지 항목·한도 설정, 결재선(승인자) 설정, 전체 내역 조회, '지급 완료' 처리 |

- 한 사용자가 여러 역할을 겸할 수 있다 (예: 대표 = 결재자 + 관리자).
- **계정 발급:** 외부 자가가입 차단. 관리자가 계정을 생성하고 초기 비밀번호를 발급한다.

## 4. 기술 구조 (Architecture)

```
📱 브라우저 / 휴대폰(PWA)
        ↓
⚡ Next.js (App Router) + shadcn/ui  — Vercel 배포
        ↓
🟢 Supabase
   🔐 Auth (로그인·계정)
   🗄 Postgres (데이터)
   📦 Storage (영수증·자료 파일)

🔄 코드 → GitHub(mltax)에 commit → Vercel 자동 배포
```

- **프론트엔드:** Next.js(App Router, TypeScript) + shadcn/ui + Tailwind CSS
- **백엔드/데이터:** Supabase (Postgres + Auth + Storage)
- **권한 제어:** Supabase RLS(Row Level Security)로 역할 기반 접근 제어
- **배포:** GitHub(mltax) → Vercel 연동, push 시 자동 배포
- **앱 확장:** 1차는 PWA(휴대폰 홈화면 설치)로 대응, 이후 필요 시 네이티브

## 5. 데이터 모델 (Data Model — 1차)

| 테이블 | 주요 컬럼 | 설명 |
|--------|-----------|------|
| `users` | id, name, email, role, department, is_active | 직원/계정. role: staff·approver·admin |
| `welfare_items` | id, name, monthly_limit, is_active | 복지 항목과 한도. 관리자가 관리 |
| `welfare_claims` | id, user_id, item_id, amount, reason, status, approver_id, approved_at, paid_at, reject_reason | 복지 청구 건 |
| `attachments` | id, claim_id, file_path, file_name | 청구 증빙 파일 (Storage 연결) |
| `posts` | id, author_id, category, title, body, is_notice, created_at | 자료실 글 / 공지 |
| `post_files` | id, post_id, file_path, file_name | 자료실 첨부 파일 |

- **welfare_claims.status:** `draft`(작성중) → `pending`(승인 대기) → `approved`(승인됨) → `paid`(지급 완료), 또는 `rejected`(반려)
- 복지 항목 초기 목록(관리자가 수정 가능): 경조사비, 의료비, 자기계발비, 도서구입비, 식대, 명절/생일 선물 등

## 6. 핵심 흐름 (Flows)

### 6.1 복지 청구 — 결재 (1단계 승인)
1. **직원**: 복지 항목 선택 → 금액·사유 입력 → 증빙 첨부 → 결재자 자동 지정 → 제출 (`pending`)
2. **결재자**: 승인 대기함에서 건별 확인 → **승인**(`approved`) 또는 **반려**(`rejected`, 사유 필수)
3. **관리자**: 승인된 건을 실제 지급 후 '지급 완료'(`paid`) 체크 — 정산 추적용
4. 반려 시 사유와 함께 신청자에게 반송, 신청자는 수정 후 재제출 가능

> 결재선은 기본 1단계지만, 향후 "팀장 → 대표" 2단계로 확장 가능하도록 `approver` 구조를 유연하게 설계한다.

### 6.2 자료실 / 공지
- 결재자·관리자가 글 작성 + 파일 업로드, 카테고리(예: 사내양식, 법규, 업무매뉴얼)로 분류
- 직원은 열람·다운로드. `is_notice`로 공지 구분 → 홈 대시보드 상단 노출

### 6.3 홈 / 대시보드
- 내 신청 현황(상태별), 결재자라면 승인 대기 건수, 최근 공지 요약

## 7. 화면 구성 (Screens — 1차)
- 로그인
- 홈 / 대시보드
- 복지 청구: 신청서 작성 · 내 신청 목록 · (결재자) 승인 대기함
- 자료실: 목록 · 상세 · 글쓰기(권한자)
- 관리자: 직원/계정 관리 · 복지 항목 설정 · 결재선 설정

## 8. 오류 처리 / 엣지 케이스 (Error Handling)
- 비활성(`is_active=false`) 계정 로그인 차단
- 권한 없는 페이지/액션 접근 시 차단(RLS + 화면 가드)
- 파일 업로드: 용량·확장자 제한, 실패 시 명확한 안내
- 결재 동시성: 이미 처리된 건 재처리 방지(상태 검증)
- 반려 시 사유 필수 검증, 금액 0 이하·항목 미선택 등 입력 검증

## 9. 보안 (Security)
- Supabase Auth + RLS로 행 단위 접근 제어 (본인 신청만 조회, 결재자만 승인 등)
- 증빙 파일은 비공개 Storage 버킷, 권한 검증된 서명 URL로만 접근
- 민감정보(영수증 등) 최소 수집·접근 통제

## 10. 테스트 (Testing)
- 단위: 상태 전이 로직(draft→pending→approved/rejected→paid), 입력 검증
- 통합: 역할별 권한(RLS) — 직원/결재자/관리자 각각 허용·차단 시나리오
- E2E(핵심 happy path): 직원 신청 → 결재자 승인 → 관리자 지급 완료
- 자료실: 업로드·다운로드·권한 분리

## 11. 향후 확장 메모
- 2차: 연차 청구·승인(잔여 연차 자동계산), 건의사항·댓글
- 3차: 푸시 알림, 네이티브 앱
- 결재선 다단계화, 복지 한도 자동 검증/경고
